## Project Overview

Masters Pool is a small fantasy golf web app for closed friend groups (2–10 players). One person creates a "game" tied to a tournament, sets the scoring rules, and shares an invite link. Each participant picks 3 golfers from the live field. As the tournament progresses, scores are pulled automatically from ESPN's public golf API, points are awarded per configurable rules (birdie/eagle/albatross/HIO and their negative mirrors for bogeys), and bonus points are awarded for tournament finish positions (1st/2nd/3rd). Two leaderboards are exposed: one for participants (sum of their 3 picks + finish bonuses) and one for every golfer in the field.

A "🍺 beer sign" appears on any participant's pick that misses the cut — that player keeps the points they earned through Friday but owes a beer per cut golfer they picked.

It is a Next.js 16 app deployed to Vercel (via GitHub auto-deploy) with Neon serverless Postgres for persistent storage.

Repository: `https://github.com/nordicaseo/masters-pool.git`

## Deployment Workflow

**Never commit directly to `main` or push to Vercel.** All work goes through feature branches:

1. **Always branch from `origin/main`** — never branch from another feature branch, or the PR will carry unrelated commits.
2. **Before every push (including to existing PRs), run `git fetch origin main` and verify your branch is based on the latest `origin/main`.** If it is not, rebase onto `origin/main` before pushing. This applies to the initial push and all subsequent pushes — never push stale branches.
3. **Before pushing, check if the current branch has already been merged to `main`** (e.g. `git branch -r --merged origin/main | grep <branch-name>`). If it has been merged, do NOT push to it. Instead, treat any further work as a new feature: create a fresh branch from `origin/main` and open a new PR.
4. Push branch, open a PR.
5. Vercel auto-deploys a preview for the PR.
6. Get review approval, then merge to `main`.
7. Merging to `main` triggers automatic production deployment.

Keep the PR description up to date. If the scope of work evolves after opening the PR, update the description to accurately and comprehensively reflect all changes.

When creating a PR with a checklist (e.g. lint, test, build), check off steps that have already been verified as passing (use `- [x]` for done, `- [ ]` for not yet confirmed).

## Architecture

### Database (Neon Serverless Postgres + Drizzle)
- Schema lives in `src/db/schema.ts` (single file — small app, no SQLite mirror needed).
- Connection in `src/db/index.ts` uses `@neondatabase/serverless` with `drizzle-orm/neon-http`. Reads `DATABASE_URL` from env.
- Migrations generated by `drizzle-kit` into `drizzle/migrations/`. Config in `drizzle.config.ts`.
- All monetary/score values stored as integers. Points are plain `integer` (can be negative for bogeys).

### Domain Model
- **`games`** — one row per pool. Holds the tournament identifier (`espn_event_id`), creator display name, the 6-char join code, and a `scoring_rules` JSONB blob (point values for each result type + finish bonuses + cut handling). Each game is self-contained.
- **`participants`** — pool members. Identified by display name + game. No email/password. Cookie `mp_user` stores the participant id once they join.
- **`golfers`** — the field for a given game. Seeded once when the game is created by hitting ESPN. `(game_id, espn_athlete_id)` is unique.
- **`picks`** — `(participant_id, golfer_id)`. Exactly 3 per participant. Locked on submit.
- **`scoring_events`** — append-only event log. `(game_id, golfer_id, kind, round, hole)` is unique so cron re-runs are idempotent. `kind` is one of `birdie | eagle | albatross | hole_in_one | bogey | double_bogey | triple_plus | finish_1 | finish_2 | finish_3 | missed_cut`. `points` is denormalized at insert time using the game's scoring rules so changing rules later does not retroactively rewrite history.

### ESPN Integration (`src/lib/espn.ts`)
- Pulls from `https://site.api.espn.com/apis/site/v2/sports/golf/leaderboard?league=pga&event=<eventId>`.
- During live rounds, ESPN exposes per-hole shot data under each competitor's `linescores` per round. We diff against existing `scoring_events` rows by `(round, hole)` and only insert the new ones.
- Final position bonuses are awarded once the tournament status flips to "post" / "final" and the leaderboard is sorted. Ties: tied golfers share the bonus pool evenly, rounded down.
- Missed cut: detected via competitor status `cut`. Inserts a single `missed_cut` event with `points: 0` so the UI can render the 🍺 badge.

### Scoring Engine (`src/lib/scoring.ts`)
- `pointsForKind(rules, kind)` resolves a point value from the game's `scoring_rules` JSON.
- `userTotals(gameId)` and `golferTotals(gameId)` are SQL aggregations: sum of `points` per participant (via picks) and per golfer.

### Cron (`src/app/api/cron/refresh-scores/route.ts`)
- Vercel Cron config in `vercel.json` runs every 5 minutes during the tournament window.
- Verifies `Authorization: Bearer $CRON_SECRET`, fetches ESPN, diffs, inserts new events.
- For every active game in the DB, fetches once. Tournaments share an event id so the ESPN call is cached per-invocation.

### Auth (No Provider)
- No accounts, no email. A participant joins by entering a display name + 6-char game code. The server creates a `participants` row and sets a signed cookie `mp_user=<participantId>` (HTTP-only, SameSite=Lax, 90-day expiry).
- Cookie signing uses `AUTH_SECRET` (HMAC-SHA256). See `src/lib/auth.ts`.
- The game creator gets the same cookie plus is recorded as the game's `created_by` participant.

### Frontend
- React 19 with Next.js 16 App Router. Path alias `@/*` maps to `./src/*`.
- Tailwind CSS v4. No component library — keep it minimal, hand-rolled HTML + Tailwind. lucide-react icons if/when needed.
- Custom theme tokens in `src/app/globals.css`: course palette (`fairway`, `fairway-deep`, `fairway-light`, `sand`, `sand-light`, `flag`, `podium`, `podium-soft`, `cream`) and a display font (`font-display` → Fraunces). Raw CSS vars live on `:root`; `@theme inline` maps them to Tailwind utilities so dark-mode overrides via `prefers-color-scheme` still apply.
- Routes:
  - `/` — landing: golf-themed hero, join form, and link to create.
  - `/games/new` — create form. Server-side fetches the PGA season schedule via `fetchSeasonSchedule(year)` (in `src/lib/espn.ts`) and renders upcoming/in-progress events as selectable cards. The picker auto-fills the ESPN event id + tournament name; if ESPN is unreachable the form falls back to a manual entry block.
  - `/games/[code]` — game home: scorecard-style leaderboards (pool + field) with a "Public pool" badge.
  - `/games/[code]/join` — display-name picker.
  - `/games/[code]/pick` — pick N golfers (only if you haven't yet).

### Next.js 16 Notes (Important)
- `params` and `searchParams` in `page.tsx` and `route.ts` files are **promises** — always `await` them.
- `cookies()` and `headers()` from `next/headers` are **async** — always `await` them.
- Route handlers live in `src/app/api/**/route.ts` and export named HTTP functions (`GET`, `POST`, …).
- Route segment config: `export const dynamic = 'force-dynamic'` on any route that reads cookies or hits the DB at request time.
- The global helper types `PageProps<'/games/[code]'>` and `RouteContext<'/api/games/[code]'>` are auto-generated and available without import.

## Key Conventions

### Error Handling — No Silent Failures
**Every `catch` block must surface the error.** Do not swallow errors with bare `.catch(() => null)`, empty catch blocks, or untouched failures. Errors must be visible in server logs and, where appropriate, returned to the user.

**Required pattern for catch blocks:**
```typescript
import { logError } from '@/lib/log';

try {
  await riskyOperation();
} catch (error) {
  logError(error, {
    subsystem: 'area_name',
    operation: 'what_failed',
    extra: { gameId, participantId },
  });
  // Then handle gracefully (fallback, return error response, re-throw, etc.)
}
```

**Required pattern for `.catch()` chains with fallbacks:**
```typescript
const result = await fetchSomething().catch((err) => {
  logError(err, { subsystem: 'area_name', operation: 'what_failed' });
  return null; // fallback value
});
```

`logError` (in `src/lib/log.ts`) writes a structured `console.error` line that includes `subsystem`, `operation`, the error message, the stack, and the `extra` context. On Vercel these surface in the Functions log and can be searched. Since this is a small app we deliberately do not use Sentry, but the discipline of always logging with structured tags is non-negotiable so issues are not lost.

**Tags convention:** Always include `subsystem` (e.g. `espn`, `scoring`, `cron`, `auth`, `db`) and `operation` (e.g. `fetch_leaderboard`, `award_finish_bonus`, `verify_cookie`). Add `extra` context like `gameId`, `golferId`, or `eventId` when available.

**API routes must always return a JSON error body with a non-2xx status on failure** — never throw an unhandled exception that produces an HTML error page. Use `return Response.json({ error: '...' }, { status: 400 })`.

**Intentional fire-and-forget exceptions:** Stream cleanup (`.cancel().catch(() => {})`) and similar truly non-critical operations may use bare `.catch(() => {})`, but only when failure would never indicate a real problem.

### Other Conventions
- ESLint flat config (`eslint.config.mjs`) with `eslint-config-next` (core-web-vitals + TypeScript). Unused vars prefixed with `_` are allowed.
- Vitest with jsdom environment. Tests live in `src/test/` and must match `src/test/**/*.test.ts(x)`.
- Drizzle config points to `src/db/schema.ts`; migrations output to `drizzle/migrations/`.
- All input validation goes through Zod schemas in `src/lib/validation.ts`.
- Server actions and route handlers should validate input first, then do work, then return.
